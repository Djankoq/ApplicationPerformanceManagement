# Анализ производительности Application Performance Management

## Тип приложения и нагрузка

Application Performance Management — учебный многопоточный REST-сервис для сравнения обычных и виртуальных потоков Java при блокирующем ожидании. `GET /work/platform` отправляет задачу в пул из 16 обычных потоков, а `GET /work/virtual` запускает виртуальный поток на задачу. Оба метода принимают `delayMs` от 1 до 5000 мс и `fail`, который позволяет вернуть HTTP 503 после задержки. Успешный ответ содержит заданную задержку, имя и тип рабочего потока. Вызов `Thread.sleep` имитирует ожидание внешнего I/O. Проект работает без БД и внешних API. [Описание запуска и API](../README.md) · [Контроллер](../src/main/java/org/example/WorkController.java).

**Технологии.** Java 21, Spring Boot 3.5.7, Spring MVC и встроенный Tomcat, `CompletableFuture` и `ExecutorService`, Actuator, Micrometer, Prometheus, Grafana, Apache JMeter. Стенд можно запустить локально или через Docker Compose. Прикладная архитектура — монолит с двумя HTTP-маршрутами в одном процессе JVM. [Зависимости Maven](../pom.xml) · [Docker Compose](../compose.yml).

**Ресурсоёмкие операции.** Во время `Thread.sleep` обычный поток остаётся занят, поэтому параллельные запросы могут ждать в очереди. Незавершённые задачи удерживают объекты в памяти. В профиле `gc-leak` дополнительную нагрузку создают выделение массивов, их накопление в heap и последующие сборки мусора. HTTP-ответы содержат несколько полей, а обработка запроса не включает тяжёлые вычисления.

## 1. Контекстное переключение и число потоков

**Как проявляется.** `newFixedThreadPool` ограничивает исполнение 16 задачами и складывает остальные задачи в неограниченную очередь. При `delayMs=500` ожидаемый предел составляет `16 / 0,5 ≈ 32 запроса/с`. С 64 клиентами, каждый из которых отправляет следующий запрос после ответа, задачи продолжают поступать и часть запросов ждёт освобождения потока. При длительном открытом потоке запросов выше пропускной способности очередь может расти, увеличивая задержку и расход heap. [Конфигурация исполнителей](../src/main/java/org/example/ThreadConfiguration.java) · [Java 21: Executors](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html#newFixedThreadPool(int,java.util.concurrent.ThreadFactory)).

**Почему риск подтверждён.** 21 ноября 2026 года выполнены два отдельных прогона на Windows с Java 21.0.1, одинаковым ожиданием 500 мс и 64 клиентами. После 6 секунд прогрева скрипт дважды считал Micrometer `COUNT` и `TOTAL_TIME` примерно с 10-секундным интервалом. Сервер использовал один и тот же HTTP-транспорт для обоих маршрутов. Все ответы нагрузочного клиента были HTTP 200. [Снимки Actuator в JSON](performance-evidence/benchmark.json) · [Скрипт замера](../scripts/benchmark.py).

| Маршрут | COUNT₁ → COUNT₂ | Завершено в окне | Запросов/с | Среднее время запроса |
| --- | ---: | ---: | ---: | ---: |
| `/work/platform` | 177 → 497 | 320 | 31,99 | 2,045 с |
| `/work/virtual` | 705 → 1985 | 1280 | 127,89 | 0,509 с |

При той же операции среднее время выросло примерно до 2 секунд у обычного пула. Пропускная способность около расчётного предела и разница между маршрутами указывают на ожидание рабочего потока. Число переключений контекста в этом прогоне не измерялось. Если сильно увеличить `WORK_PLATFORM_THREADS`, больше обычных потоков будут одновременно просыпаться и конкурировать за CPU. Этот риск проверяется отдельно.

![Два маршрута под одинаковой нагрузкой. Обычный пул выполняет около 32 запросов в секунду при среднем времени ответа 2,045 с.](performance-evidence/platform-vs-virtual.png)

*Рис. 1. Экспорт двух окон измерений Actuator. Пунктир отмечает расчётный предел обычного пула и заданную обоим маршрутам задержку.*

**Как обнаружить и устранить.** Адаптировать план JMeter для раздельных прогонов с одинаковым `delayMs`, повышая параллельность через значения 8, 16, 32 и 64. В Grafana сравнить Rate, p95 Duration и Errors по URI. Для прямого замера очереди добавить через Micrometer число активных рабочих потоков и длину очереди. Стек `platform-worker-*` в VisualVM или `jcmd <PID> Thread.print` покажет, чем заняты рабочие потоки. Чтобы проверить накладные расходы при увеличении пула, сравнить число переключений потоков процесса Java на один завершённый запрос при одинаковом профиле нагрузки через Windows Performance Analyzer, график CPU Usage (Precise). [План JMeter](../jmeter/api-users.jmx) · [Панель Grafana](../monitoring/grafana/dashboards/apm-red.json) · [Руководство Microsoft по анализу CPU](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis#cpu-usage-precise-graph).

Для этой блокирующей операции использовать виртуальные потоки. При подключении реальной БД или внешнего API ограничить число одновременных обращений к зависимости и задать тайм-аут вызова. Если нужен обычный пул, задать очередь конечного размера в `ThreadPoolExecutor`, возвращать HTTP 503 при её заполнении и проверять под нагрузкой, что задержка контролируется, а перегрузка видна в метриках.

## 2. Архитектура — монолит и общие ресурсы JVM

**Как может проявиться.** Оба HTTP-маршрута упакованы в один JAR, используют одну реализацию `blockingWork` и запускаются с разными рабочими исполнителями. Их HTTP-транспорт, CPU и heap общие. Если один маршрут исчерпает общий ресурс, задержки могут вырасти на обоих маршрутах. Prometheus собирает метрики, Grafana их отображает. [Сборка приложения](../pom.xml) · [Описание сервисов Compose](../compose.yml).

**Почему монолит подходит.** Цель стенда — сравнить исполнителей на одной операции и в одинаковой среде. Разделение по двум прикладным сервисам добавило бы межсервисные вызовы или различия в среде запуска. Оба маршрута используют общий контракт ответа и одинаковую валидацию. Результат формируется из параметров запроса и свойств потока, поэтому здесь отсутствуют общие доменные данные и задачи синхронизации реплик или распределённых транзакций. Насыщение обычного пула подтверждено раздельными прогонами. Влияние перегрузки одного маршрута на второй требует отдельной проверки.

**Как обнаружить и предотвратить.** Подать нагрузку JMeter на один маршрут, а второй опрашивать с постоянной небольшой частотой. Сравнить p95 и долю ошибок второго маршрута до и во время нагрузки. Одновременно наблюдать CPU процесса, heap и паузы GC, чтобы выявить исчерпание общего ресурса. Для предсказуемой работы под смешанной нагрузкой задать раздельные лимиты одновременных запросов и контролировать их заполнение. Интеграционные тесты проверяют контракт обоих маршрутов. [Тесты API](../src/test/java/org/example/WorkIntegrationTest.java).

## 3. Среда выполнения — heap и сборка мусора

**Как проявляется.** При запуске с профилем `gc-leak` компонент `MemoryLeakExperiment` примерно каждые 100 мс добавляет массив `byte[128 * 1024]` в статический список. Сильные ссылки удерживают массивы, поэтому G1 не может освободить занятый ими heap. При `-Xms128m -Xmx128m` процесс в итоге завершился с `OutOfMemoryError: Java heap space`. [Код эксперимента](../src/main/java/org/example/MemoryLeakExperiment.java) · [Руководство по G1 в Java 21](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html).

**Почему риск подтверждён для эксперимента.** В повторном прогоне 21 ноября 2026 года процесс завершился через 99,09 с с кодом 3. Выполнено 6 полных сборок мусора. Остаток heap после них вырос с 97 до 114 МиБ. Последние две сборки показали `114M->114M` с точностью до целых МиБ. В последней выборке перед завершением 810 массивов удерживали 101,25 МиБ полезных данных. В обычном профиле этот компонент отключён, что проверяет интеграционный тест. [Строки GC и приложения](performance-evidence/gc-logs.txt) · [Сырые замеры heap](performance-evidence/heap.csv) · [Проверка профиля](../src/test/java/org/example/WorkIntegrationTest.java).

![Удерживаемые массивы заполняют heap. Уровень памяти после Full GC растёт до 114 МиБ, после чего JVM завершается с ошибкой.](performance-evidence/heap-growth.png)

*Рис. 2. Экспорт `MemoryMXBean` и GC-лога повторного прогона. Красные метки показывают остаток heap после Full GC. Последняя выборка сделана до OOM.*

**Как обнаружить и устранить.** Отслеживать объём живых объектов и частоту пауз через `jvm.gc.live.data.size` и `jvm.gc.pause` в Micrometer. Воспроизвести рост с `-Xlog:gc*` и проверить в VisualVM или heap dump, какие объекты удерживают `byte[]`. Исправление в рабочем коде — освобождать ссылки после обработки или задавать жёсткий предел объёма и удалять старые записи. Более высокий `-Xmx` при продолжающемся накоплении увеличит время до OOM. Для Docker следует выбирать heap с учётом лимита контейнера и запаса под память JVM вне heap. В текущем Compose лимиты CPU и памяти для `app` не заданы. [Метрики JVM в Micrometer](https://docs.micrometer.io/micrometer/reference/reference/jvm.html) · [Скрипт воспроизведения](../scripts/gc_experiment.py) · [Конфигурация Compose](../compose.yml).

Повторные прогоны выполнены локально на Windows. `mvnw verify` прошёл все 4 интеграционных теста. Илл. 1 и 2 построены из измерений и логов, поскольку захват окна браузера в этой среде недоступен. Команды воспроизведения и результаты предыдущих прогонов доступны в проекте. [README](../README.md) · [Предыдущие замеры](REPORT.md) · [Проверка плана JMeter](JMETER.md).
